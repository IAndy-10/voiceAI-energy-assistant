# M03.6 — Diagnóstico de errores de proveedor

## Hallazgo

La respuesta genérica HTTP 502 provenía de `VestaAgent.chat()`: el bloque `except Exception` reemplazaba cualquier excepción original por `AgentProviderError("El proveedor no pudo completar la consulta")`. Por eso Uvicorn sólo podía registrar el 502, sin tipo de SDK, estado HTTP, código ni request ID.

Además, la auditoría del payload de tools identificó una causa probable para el primer intento: se enviaba `strict=true` con tres esquemas cuyos campos opcionales no aparecían en `required` (`rank_stores`, `get_solar`, `get_chiller`). En strict mode, Responses exige que toda propiedad sea requerida; la API rechaza un esquema incompatible con un 400. El código ahora normaliza `required` a todas las propiedades y conserva tipos anulables para los parámetros opcionales.

No es posible confirmar retrospectivamente que ésa fue la causa exacta del 502 anterior: el error original ya fue descartado por la versión previa. La siguiente prueba controlada sí devolverá un código seguro y registrará la categoría y el request ID cuando el SDK lo entregue.

## Manejo actual

| Categoría | SDK/estado típico | HTTP local | Código seguro |
| --- | --- | --- | --- |
| Solicitud inválida | `BadRequestError`, 400/422 | 502 | `openai_bad_request` |
| Autenticación | `AuthenticationError`, 401 | 502 | `openai_authentication` |
| Permiso | `PermissionDeniedError`, 403 | 502 | `openai_permission` |
| Modelo/recurso | `NotFoundError`, 404 | 502 | `openai_not_found` |
| Cuota/rate limit | `RateLimitError`, 429 | 429 | `openai_rate_limit` |
| Conectividad | `APIConnectionError` | 503 | `openai_connection` |
| Timeout | `APITimeoutError` | 504 | `openai_timeout` |
| Servicio/protocolo | 5xx, `InternalServerError` o respuesta no esperada | 502 | `openai_provider_server` / `openai_protocol` |

El log seguro `agent_provider_error` contiene únicamente categoría, tipo de excepción, estado HTTP del proveedor, código del proveedor y request ID. No incluye claves, prompt, snapshot, resultados de tools ni cuerpo del proveedor. El frontend recibe un objeto seguro `{code, message, request_id?}`.

## Consumo y ledger

Antes de llamar se mantiene la reserva preventiva. Si falla antes de existir una respuesta, la reserva se libera y no se añade gasto ficticio. Si una ronda ya devolvió uso y una posterior falla, los tokens/costo conocidos permanecen contabilizados; la consulta no aumenta `completed_queries`. Esto evita tanto ocultar consumo parcialmente facturable como inventar consumo no reportado.

## Prueba controlada única

1. Revoca/rota cualquier clave que haya quedado expuesta en una consola anterior y coloque la nueva clave sólo en `.env` local.
2. Reconstruya únicamente la API:

   ```powershell
   docker compose up -d --build --force-recreate --no-deps energy-api
   ```

3. Cargue el snapshot, active OpenAI y realice **una sola** pregunta corta. No reintente automáticamente.
4. Si falla, conserve sólo la línea `agent_provider_error` (categoría, estado, código y request ID), sin copiar prompts ni datos. El request ID permite escalar el caso.
5. Revise `GET /agent/status` para observar el contador local; no borre ni reinicie el volumen `agent-usage`.

La clasificación sigue la [referencia oficial del SDK Python](https://developers.openai.com/api/reference/python) y el requisito de strict mode de la [guía de function calling](https://developers.openai.com/api/docs/guides/function-calling).
