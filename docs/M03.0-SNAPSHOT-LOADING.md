# VESTA 2.0 — M03.0: carga local de snapshots

La tarjeta **Acceso local** de `/demo` permite elegir un JSON y cargarlo con el mismo `POST /snapshot` autenticado que ya usa la API. No se agregó un endpoint de carga alternativo: el navegador lee el archivo seleccionado en memoria, verifica que sea JSON y menor a 5 MB, y lo envía sólo a `127.0.0.1:8000` con Bearer.

`GET /snapshot/status` es el único endpoint adicional. Existe para volver a mostrar, tras recargar la página, el estado que el servidor mantiene en memoria. Requiere el mismo Bearer y devuelve sólo metadatos: esquema, fecha, cantidad de fuentes y tipo; no devuelve el snapshot ni su hash.

## Tipo de datos y OpenAI

El servidor calcula SHA-256 de una serialización JSON canónica y lo mantiene sólo en memoria junto al snapshot. Un snapshot se muestra como **DEMO · Datos ficticios** únicamente si se cumplen las tres condiciones:

1. Su hash coincide con `VESTA_DEMO_SNAPSHOT_SHA256` (el valor inicial autoriza el archivo sintético entregado).
2. `generator` es exactamente `vesta-synthetic-demo-generator`.
3. Todos los archivos fuente empiezan con `demo-`.

Las dos últimas son comprobaciones adicionales; el hash es la clasificación confiable. Un archivo arbitrario, renombrado o con esos campos modificados se muestra como **Tipo no verificado** (podría contener datos REAL). No se usa ni acepta una etiqueta de modalidad enviada por el navegador.

**Usar OpenAI** es un control separado y voluntario de la pestaña. Si `OPENAI_ENABLED=false` o falta la clave en el servidor, aparece como no configurado y el control no se puede activar. Cuando el proveedor está configurado, el usuario puede activarlo para el snapshot actualmente cargado, sea DEMO o no verificado; la interfaz advierte que las consultas pueden enviar datos del archivo activo a OpenAI. Esta selección no modifica las credenciales, allowlist, presupuesto, límites ni `store=false` del backend.

Cada reemplazo crea un nuevo identificador en memoria. La página limpia resultados y conversación anterior inmediatamente; el proceso de la API no persiste snapshots ni nombres de archivo. Al recrear `energy-api` se pierde el snapshot cargado y debe importarse de nuevo.

## Uso local

```powershell
$env:ENERGY_TOOLS_API_TOKEN = "<token-local>"
docker compose up -d --build --no-deps energy-api
```

En instalaciones que exponen el binario clásico de Compose:

```powershell
docker-compose up -d --build --no-deps energy-api
```

Abra `http://127.0.0.1:8000/demo`, ingrese el token, use **Elegir JSON**, seleccione el archivo local y pulse **Cargar snapshot**. El indicador informa modo, archivo mostrado sólo en la pestaña, hora, fuentes, esquema y resultado de la validación.

No monte `Datos/` en Docker ni agregue snapshots al build. Para registrar una nueva versión del dataset DEMO ficticio, calcule su hash canónico durante una revisión controlada y actualice `VESTA_DEMO_SNAPSHOT_SHA256`; esto sólo afecta la etiqueta DEMO, no habilita ni bloquea OpenAI.

## Pruebas

```powershell
.\.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider
```

Las pruebas cubren DEMO autorizado, JSON no verificado, recambio entre snapshots, las seis herramientas, token inválido, JSON/esquema inválido, tamaño máximo, suplantación por nombre/generador y OpenAI simulado contra el snapshot activo. No se realizan llamadas reales a OpenAI.
