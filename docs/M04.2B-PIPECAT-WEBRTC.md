# M04.2-B — Cliente web Pipecat y diagnóstico ICE local

El bundle se construye sin Node instalado en Windows, mediante `node:22-alpine`.

```powershell
docker run --rm -v "${PWD}/voice_agent/web:/app" -w /app node:22-alpine npm ci
docker run --rm -v "${PWD}/voice_agent/web:/app" -w /app node:22-alpine npm run build
```

El bundle `dist/vesta-voice-client.js` usa los paquetes oficiales `@pipecat-ai/client-js` y `@pipecat-ai/small-webrtc-transport`. No abre una sesión ni contiene credenciales.

## Diagnóstico Docker Desktop / ICE

El Development Runner de Pipecat 1.14.0 completa la señalización HTTP por
`7860/TCP`, pero eso no transporta el medio WebRTC. `aiortc` abre puertos UDP
efímeros para ICE. En una red Docker `bridge`, publicar solamente el puerto
TCP de señalización deja esos candidatos sin una ruta desde el navegador y el
estado permanece en `checking` / `connecting`.

Se probó `host` networking en Docker Desktop. El motor admite el modo, pero
en Docker Desktop no se puede enlazar una IP concreta del host en ese modo.
El runner iniciado con `--host 127.0.0.1` no quedó accesible por
`127.0.0.1`, por lo que no cumple la restricción de demostración local y no se
adopta como configuración base.

`compose.webrtc-local.yaml` conserva el aislamiento bridge y aplica el
workaround propuesto por un mantenedor de Pipecat: restringir el rango
efímero del contenedor y publicar el mismo rango UDP. Todos los puertos se
enlazan a loopback; no se exponen a la LAN.

```powershell
# Requiere que la imagen vesta-pipecat-voice-agent:0.4.2 ya esté construida.
docker compose -f compose.webrtc-local.yaml --profile webrtc-local up -d

# Abrir manualmente en Chrome y pulsar Connect.
Start-Process 'http://127.0.0.1:7861/client/'

# Evidencia esperada tras conectar: on_client_connected y ICE connected.
docker compose -f compose.webrtc-local.yaml logs --tail 120 voice-agent-webrtc-local

# Detener solo la prueba temporal al finalizar.
docker compose -f compose.webrtc-local.yaml --profile webrtc-local down
```

En Chrome, abra `chrome://webrtc-internals` en otra pestaña antes de pulsar
**Connect**. La validación se considera exitosa únicamente si el navegador
muestra una pareja ICE seleccionada y estado `connected`/`completed`, y el
log del runner contiene `SmallWebRTC client connected`. Pulsar
**Disconnect** debe registrar `SmallWebRTC client disconnected`. Un `POST
/start` o `POST /offer` con HTTP 200 por sí solo no demuestra conectividad de
medios.

La configuración de prueba limita los puertos UDP 40000--40100 mediante
`net.ipv4.ip_local_port_range` y publica exclusivamente
`127.0.0.1:40000-40100/udp`. El rango procede del workaround documentado en
la discusión de Pipecat; su eficacia debe validarse en Chrome antes de
integrarlo en la demo. No contiene STUN/TURN ni credenciales, y no inicia
proveedores externos.

Si la negociación sigue sin llegar a `connected`, no debe ampliarse el rango
ni añadir direcciones arbitrarias: el siguiente paso es configurar un TURN
local con puertos de relay fijos y volver a verificar los pares ICE.

## Runner TURN: descubrimiento de `bot`

Pipecat 1.14.0 busca `bot(runner_args)` en el módulo ejecutado como
`__main__`. El launcher TURN se inicia con
`python -m voice_agent.webrtc_turn_runner`; por eso dicho módulo reexporta el
`bot` del pipeline mínimo de `webrtc_runner`. No duplica el pipeline. Una
oferta SDP válida debe dejar en los logs `webrtc_connection_callback executed
successfully` y `PipelineWorker ... ready`. Esos mensajes validan la carga
del bot, no la conectividad ICE: esta última sólo está confirmada al llegar a
`connected` y emitir `SmallWebRTC client connected`.
