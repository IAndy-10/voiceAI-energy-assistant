# M04.7 — Diagnóstico WebRTC en Docker Desktop Windows

## Alcance y evidencia

Este documento cierra la investigación del runner `voice-agent` en Docker
Desktop Windows. No cambia la alternativa validada de Windows nativo
(`scripts/start-voice-windows.ps1`) ni la configuración compartida que usa
Ítalo en macOS.

La inspección inicial se hizo sin reconstruir imágenes. Tras concluir los
experimentos, `voice-agent` y `turn-local` quedaron detenidos en Windows; la
API se configura con `compose.windows-voice.yaml` para usar el runner nativo
en `:7861`.

## Configuración efectiva observada

`compose.yaml` crea coturn con un rango pequeño de relay `49160–49169`, pero
solo publica el puerto de control/allocación `3478`. No define `external-ip`,
`relay-ip` ni `listening-ip`. Por tanto coturn detecta y anuncia su dirección
Compose `172.30.0.4`; sus logs confirman tanto la detección como la
inicialización de ese relay.

El runner crea credenciales REST temporales en
`voice_agent.webrtc_turn_runner`, usando `PIPECAT_TURN_HOST=turn-local,127.0.0.1`.
Pipecat entrega esas URLs a ambos pares. Es necesario conservar
`turn-local` como la primera URL para aiortc dentro de Compose; Chrome debe
usar una URL y dirección que pueda alcanzar desde Windows.

Esta topología explica el estado observado: la oferta/answer SDP puede
completar señalización, pero ICE pasa de `checking` a `disconnected`/`failed`
cuando intenta pares que no son enrutables desde el host.

## Aviso `CONFIG: Unknown argument:` de coturn

El aviso aparece una vez durante el arranque, después de que coturn acepta el
realm. Aun con el aviso, el proceso sigue activo, crea los relay sockets y
registra asignaciones TURN; por ello no explica por sí solo el fallo ICE.

La inspección segura confirmó que no hay argumentos vacíos y que los únicos
puertos publicados son `3478/tcp` y `3478/udp`. Aún no hay evidencia suficiente
para atribuir el aviso a una opción concreta sin exponer el argumento que lleva
el secreto. La comprobación focalizada propuesta es arrancar coturn con el
mismo conjunto de flags, uno por uno, en un override temporal de diagnóstico y
comparar el log; no debe hacerse como parte de la implementación sin aprobar
el plan. Mientras coturn asigne relays, el aviso se clasifica como secundario.

## El HTTP 404 es un problema separado

El cliente Pipecat construye la ruta de oferta como
`/sessions/{sessionId}/api/offer` a partir de la respuesta de `/start`. En
Pipecat 1.14 esa ruta responde 404 cuando el `sessionId` no está en
`active_sessions`; el runner lo elimina al terminar la tarea del bot.

Por ello un 404 puede resultar de una reconexión o PATCH ICE tardío para una
sesión ya cerrada, de una recarga/reinicio del runner entre `/start` y `/offer`,
o de una URL/sesión distinta. No hay evidencia de que sea causado por la falta
de relay. La próxima captura debe registrar, sin cuerpos ni tokens, método,
ruta, código, `sessionId`, `pc_id` y la secuencia temporal `/start` → `offer`
→ PATCH para determinar cuál hipótesis se cumple.

## Comparación de plataformas

macOS e Windows comparten la red virtual de Docker Desktop, pero las rutas
host↔VM/NAT son implementadas por plataformas distintas. La configuración
actual fue descrita para macOS y no prueba que un relay anunciado como IP
Compose sea enrutable desde Chrome en Windows. No se debe cambiar el archivo
compartido basándose en este diagnóstico: el arreglo debe comenzar como
override Windows y macOS debe conservar el flujo actual hasta validar su propia
conexión ICE.

## Corrección de seguimiento

La primera corrección con `external-ip=127.0.0.1` no puede funcionar para
ambos extremos: para Chrome, `127.0.0.1` es Windows; para aiortc dentro de
`voice-agent`, es el propio contenedor. Además, aunque Windows resuelve
`host.docker.internal` a su IP LAN, el contenedor lo resuelve a la puerta de
enlace Docker, por lo que ese nombre tampoco ofrece una dirección común.

El override Windows debe anunciar una IP LAN explícita de Windows y publicar
`3478` más el rango relay en esa misma interfaz. Es una dirección alcanzable
tanto por Chrome como por un contenedor que vuelve al host a través de NAT. El
valor se proporciona solo al proceso Compose como `WINDOWS_TURN_EXTERNAL_IP`;
no se guarda en `.env` ni contiene un secreto.

El override también reemplaza `PIPECAT_TURN_HOST` para el runner Docker.
Pipecat reutiliza una sola lista ICE para aiortc y Chrome; conservar
`turn-local` en esa lista seguiría entregando al navegador un hostname DNS
interno. La IP LAN explícita es la única URL TURN publicada para ambos pares.

## Conclusión

La causa del ICE fallido es la falta de una ruta UDP común y alcanzable entre
Chrome y el peer dentro de Docker Desktop. La señalización, el grant de sesión
y el pipeline no son causas de ese fallo de transporte. Docker Windows no se
declara funcional para WebRTC.

## Experimento directo sin STUN/TURN

`compose.windows-direct-webrtc.yaml` es un override exclusivo para Docker
Desktop Windows. Sustituye solamente el comando de `voice-agent` por
`voice_agent.webrtc_runner` y fija `PIPECAT_ICE_SERVERS` vacío. No modifica
`turn-local`, `compose.yaml` ni el runner nativo de Windows.

En Pipecat 1.14, el handler `SmallWebRTCRequestHandler` recibe esa lista tanto
para el peer aiortc del runner como para `iceConfig` que se devuelve a Chrome.
Cuando la lista está vacía, aiortc anuncia únicamente candidatos `host`. El
cliente de Vesta no solicita `enableDefaultIceServers`, por lo que `/start`
tampoco habilita el STUN público de reserva de Pipecat. De ese modo ambos
extremos quedan realmente sin STUN/TURN.

La configuración efectiva publicó únicamente `127.0.0.1:7860/tcp`. Ese puerto
es solo señalización HTTP: no publica el UDP dinámico de candidatos host. El
contenedor solamente puede anunciar su IP de bridge Compose (`172.30.x.x`), que
Chrome de Windows no puede enrutar en Docker Desktop. Por tanto no hay un par
de candidatos host alcanzable por diseño y no se espera que ICE llegue a
`connected` ni `completed` en esta topología.

El runner directo arrancó sano y sin el wrapper TURN. No se registró un estado
ICE ni un candidate pair de Chrome porque no había una pestaña Vesta disponible
para realizar la única prueba manual autorizada; no se interactuó con las
pestañas Chrome ajenas. Esta ausencia no constituye éxito ni fracaso de ICE.

## Decisión final

- **Windows:** Pipecat nativo, con API Docker mediante
  `compose.windows-voice.yaml`.
- **macOS:** se conserva sin cambios el flujo Docker existente para la
  validación independiente de Ítalo.
- **Producción candidata:** Linux + Docker Compose, pendiente de comprobar
  ICE `connected`/`completed`, candidate pair seleccionado y audio real.

Los overrides de TURN y de ICE directo fueron diagnósticos reversibles; no son
configuración soportada para Windows ni deben incluirse en el PR.
